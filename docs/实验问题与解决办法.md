# 实验问题与解决办法

> 2026.10 GRPO / RLVR 实验过程中实际踩到的坑，按出现顺序记录。
> **每一节的最后一条「通用启示」才是真正值钱的东西** —— 面试和报告里讲那个。
>
> 这些问题的共同特征：**大部分不报错**。它们只是让训练悄无声息地不工作。

---

## 一、环境类

### 1. 装了 CPU 版 PyTorch

| | |
|---|---|
| **现象** | `torch.cuda.is_available()` 返回 `False`，但机器明明有显卡 |
| **根因** | `pip install torch` 默认装 CPU 版；要 CUDA 版必须指定 index-url |
| **解决** | 去 pytorch.org 选对应 CUDA 版本，用它生成的命令装 |
| **通用启示** | **深度学习环境的第一件事永远是验证 `cuda.is_available()`。** 这一条不过，后面所有"训练很慢""跑不动"都是幻觉 |

### 2. Python 版本太老

| | |
|---|---|
| **现象** | 装 trl / transformers 新版时报依赖冲突 |
| **根因** | 系统 Python 3.9，新版库要求 3.10+ |
| **解决** | 用 WSL Ubuntu 24.04 自带的 Python 3.12 建 venv |
| **通用启示** | 别用系统 Python。**venv 隔离 + 较新的解释器**，是深度学习环境的基本盘 |

### 3. HuggingFace 连不上——表现是"卡住"而不是报错

| | |
|---|---|
| **现象** | `load_dataset(...)` 或 `from_pretrained(...)` 卡住不动，几分钟没输出，**不报错** |
| **根因** | 默认连 `huggingface.co`，该域名被墙，TCP 连接一直等超时 |
| **解决** | `export HF_ENDPOINT=https://hf-mirror.com`（**必须在 import 之前**）。同时写进 `~/.bashrc`，并在脚本顶部加 `os.environ.setdefault(...)` 兜底 |
| **通用启示** | **"卡住"和"报错"要分开排查。** 网络问题的典型表现是静默等待。脚本自己兜住环境变量，比依赖用户的 shell 配置可靠 |

## 二、模型使用类

### 4. Qwen3 的思考模式：默认是**开**的

| | |
|---|---|
| **现象** | 训练时 8 条回答全被长度上限截断，奖励恒为 0，`loss ≈ 0`，**不报错** |
| **根因** | Qwen3 的 chat template 写的是 `{% if enable_thinking is defined and enable_thinking is false %}` —— **只有显式传 `False` 才关掉**。不传参数 = 思考模式开着，模型会先写一大段 ` thinking` 再作答 |
| **解决** | `apply_chat_template(..., enable_thinking=False)`；TRL 里是 `GRPOConfig(chat_template_kwargs={"enable_thinking": False})` |
| **通用启示** | **"默认值"是最容易踩的坑**，尤其是反直觉的默认值。判断方法：把模型的**实际输出原文**打出来看，而不是只看指标。我们就是这么发现 Prompt 里那段空的 `<think>\n\n</think>` 的 |

### 5. 答案抽取正则太贪

| | |
|---|---|
| **现象** | 单元测试发现 `"The answer is 300."` 被抽成 `'300.'`（带句号） |
| **根因** | 正则用了 `[\d,\.]+`，把句末句号也吞了 |
| **解决** | 改成 `-?\d[\d,]*(?:\.\d+)?` —— **必须以数字开头**，小数部分单独可选 |
| **通用启示** | **奖励函数的抽取逻辑必须写单元测试。** 这类 bug 不报错，只让一批本来正确的回答拿不到分，训练信号被静默削弱 |

## 三、GRPO 算法实现类

### 6. logits 与 label 的错位

| | |
|---|---|
| **现象** | 算 per-token logprob 时形状对不上，或算出来的概率不合理 |
| **根因** | `logits[t]` 预测的是**位置 `t+1`** 的 token，不是 `t` |
| **解决** | `logits[:, :-1, :]` 配 `input_ids[:, 1:]` —— **两边各丢一个，丢的是不同的东西**：logits 丢最后一个（它要预测的不存在），input_ids 丢第一个（没有位置预测它） |
| **通用启示** | 自回归模型里**下标永远差一位**。梳理清楚"哪个位置预测哪个 token"是读懂所有训练代码的前提 |

### 7. `loss.backward()` 前忘了 `zero_grad()`

| | |
|---|---|
| **现象** | 梯度越累加越大，训练发散 |
| **根因** | PyTorch 的 `.grad` 是**累加**语义，不是覆盖 |
| **解决** | 训练循环里 `zero_grad() → backward() → step()` 固定顺序 |
| **通用启示** | 基础但致命。这是训练循环里唯一"顺序错了就静默出错"的地方 |

### 8. 组内奖励无差异 → 优势恒为 0 → 梯度为 0

| | |
|---|---|
| **现象** | `loss` 恒为 0.0000，`reward` 不动，训练像在空转 |
| **根因** | GRPO 的优势是 `A_i = (r_i - 组内均值) / 组内标准差`。**一组回答全对或全错时，标准差为 0，这个公式本身失去定义**，优势全 0 |
| **解决** | ① 把题目难度调到模型能力边界；② **筛选训练数据，只保留有差异的题**（见第 12 条） |
| **通用启示** | **"没有差异就没有信号"不是工程巧合，是公式的数学结构决定的。** 这是整个 RLVR 领域最核心的工程约束，DAPO 的「动态采样」就是冲它去的 |

## 四、TRL 集成类

### 9. `completions` 不是字符串，是对话格式的列表

| | |
|---|---|
| **现象** | `TypeError: expected string or bytes-like object, got 'list'` |
| **根因** | 数据集用对话格式（`[{"role":"user",...}]`）时，TRL 返回的 completion 也是同构的：`[{"role":"assistant","content":"..."}]` |
| **解决** | 写 `to_text()` 统一处理 `str` / `[dict]` / 嵌套三种形态 |
| **通用启示** | **先打印出实际拿到的数据类型再写处理逻辑。** 我们的 `[诊断]` 打印一眼就暴露了 `prompts[0]` 是对话格式，由此推断 completion 同构 |

### 10. batch 必须能被 `num_generations` 整除

| | |
|---|---|
| **现象** | `ValueError: The global eval batch size (1 * 1) must be divisible by the number of generations used for evaluation (4)` |
| **根因** | **一个 prompt 的 G 条回答必须落在同一个 batch 里** —— 优势是组内算的，拆开就崩 |
| **解决** | 训练：`per_device_train_batch_size × gradient_accumulation_steps % G == 0`；验证：`per_device_eval_batch_size % num_generations_eval == 0` |
| **通用启示** | 这个约束**所有 GRPO 实现都有**（手写版因为一个 step 只处理一个 prompt 才没撞上）。**库宁可报错也不让你配出错误的优势计算**，这个设计值得学 |

## 五、训练调优类

### 11. 默认学习率调度在短训练下"自残"

| | |
|---|---|
| **现象** | 60 步的 run 里 `learning_rate` 从 1e-5 掉到 1.67e-7，**后一半几乎没在学** |
| **根因** | `lr_scheduler_type` 默认是 `"linear"`，在 `max_steps` 处衰减到 0 |
| **解决** | 短训练用 `lr_scheduler_type="constant"` |
| **通用启示** | **默认配置是为"大规模训练"设计的，小实验直接套用会得到误导性结论。** 看指标时要把 `learning_rate` 一起看——否则你会把"LR 归零"误判成"模型学不动" |

### 12. 大部分样本产生不了梯度 —— 数据筛选是最大的杠杆

| | |
|---|---|
| **现象** | 未筛选时 `frac_reward_zero_std ≈ 40~50%`；训练集 reward 平，**验证集 reward 反而下降** |
| **根因** | 模型对单道题几乎"要么必对要么必错"，边界样本稀缺。**未筛选时 70%+ 的算力花在不产生梯度的样本上** |
| **解决** | 训练前对每题采样 G 次，**只保留有对有错的题**（`filter_data.py`）。验证集不筛，保持真实分布 |
| **效果** | **验证集通过率从 26.3% 提升到 56.9%**（同样的模型、步数、超参，唯一变化是数据） |
| **通用启示** | **这是整个项目最大的单点收益。** 而且它说明：在 RLVR 里，**数据质量（难度分布）比调超参重要得多** |

### 13. 回答越训越长（length hacking）

| | |
|---|---|
| **现象** | `completions/mean_length` 从 ~90 涨到 150~300，多步撞上 `max_completion_length` 上限 |
| **根因** | 奖励函数抽的是**最后一个数字** —— 回答越长，"最后出现正确数字"的机会越多。模型学会了刷这个空子 |
| **解决** | 尚未彻底解决；候选方向是**长度惩罚项**或**格式奖励**（要求答案包在 `\boxed{}` 里） |
| **通用启示** | **奖励函数一旦写错，模型一定会找到空子。** 而且它不会"作弊得很难看"—— 它只是把长度慢慢拉长，指标看起来还在涨。这是 reward hacking 的标准形态 |

## 六、方法论层面（最值得写进报告）

### 14. 验证集不能按训练集的标准筛

如果验证集也筛成"刚好一半对"，`eval_reward` 会天然固定在 0.5 附近 —— **它就不再衡量"模型有多好"，只是在重复你的筛选标准。**

**验证集必须保留真实分布**，否则你量的是自己的筛子，不是模型。

### 15. 跨轮对比必须先确认验证集没变

第一轮验证集是 GSM8K 第 300–360 题，第二轮换成第 3000–3080 题。**两轮的 `eval_reward` 数字不可直接比较。**

**轮内对比成立**（同一验证集，step 20 → 80），这才是能写进报告的结论。

> 实验记录里一定要写明**每一轮用的是哪份验证集**。这个细节漏了，所有跨轮结论都作废。

### 16. "指标在动"不等于"模型在学"

必须同时看：`train reward` / `eval reward` / `mean_length` / `kl` / `frac_reward_zero_std`。

- train 涨 + eval 涨 → 真学到
- train 涨 + eval 不涨 → 过拟合
- **train 平 + eval 降 → 完全没学到（第一轮的情况）**
- train 涨 + length 涨 → 可能是 reward hacking

**单一指标会骗人。**
